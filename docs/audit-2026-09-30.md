# Full audit — end of September 2026

- Date: 2026-09-30
- Scope: bugs and security, layering and responsibilities, duplication and dead code, error handling, tests and the coverage gate, performance, documentation against the code.
- Snapshot: 220 commits, 32 ADRs, `main` at `a2aebb6` (PR #89), version `0.1.0-alpha.9`.
- Method: a direct read of the largest and most-changed files (`src/renderer/app.tsx`, `src/application/workflows/single-input.ts`, every handler in `src/main/ipc`, the preload and the bridge type, the OPDS server, the library and pending-run stores), a partial read of `MappingEditor` and the settings editor, and measurements from scripts written for this audit: the import graph of `src` (cycles, fan-in and fan-out), function length and branch count from the TypeScript syntax tree, an exported-but-unreferenced scan, `git log` churn, and a check that every file path named in the docs exists. Two findings (1 and 2) were reproduced by running the code in throwaway tests that were not kept.

This is a report, not a plan. It names what is wrong, where, and what the direction is; deciding what becomes a pull request, and in what order, is a separate step. It follows [the 2026-09 audit](audit-2026-09.md), whose first nine items have shipped, and reopens one of its decisions (finding 6).

**What was not read.** The parsers in `adapters/mangabind/protocol.ts` and `adapters/mangapress/protocol.ts`, the OPDS feed and XML builders, `domain/mapping.ts` beyond its exports, the validation inside `domain/output-profile.ts`, the CI workflows, the packaging scripts, the end-to-end specs and most stories. Nothing here says those are clean.

## What is already working well

- **The layers hold.** The import graph over `src` has one cycle, between two domain files and only through types (finding 12), and the layer rule the earlier audit asked for is now enforced by `lint:boundaries` rather than by review.
- **The window is configured the way Electron's guidance asks.** `contextIsolation`, `sandbox` and a denied `nodeIntegration`, a denied `window.open`, blocked in-page navigation (`src/main/window.ts`), and a Content-Security-Policy in `src/renderer/index.html`.
- **Every IPC handler that was read validates its input with a zod schema** before using it.
- **The coverage gate is real where it applies.** `vitest.config.ts` demands 100% of branches, functions, lines and statements over the layers it names, and `npm run check` runs it.
- **The documentation is accurate about files.** Every repository path named in the README, the docs and the per-directory READMEs exists, and `docs/adr/README.md` lists all 32 ADRs.

## Findings — bugs and security

### 1. The OPDS server can be made to serve a file outside the shared folder

**Where:** `src/library/manifest.ts:43` (`relativePath: z.string().min(1)`) and `serveBook` in `src/adapters/opds/http-server.ts`.

**Problem:** only the writing side checks that a book lives inside the library (`toLibraryRelativePath` refuses `..` and absolute paths). The reading side trusts `library.json`: the schema accepts any string, and `serveBook` joins it onto the library path. A library whose `library.json` holds `"relativePath": "../outside-secret.epub"` answered `GET /books/..%2Foutside-secret.epub` with **200 and the contents of a file outside the folder**. This was reproduced against a real `NodeOpdsServer` on `127.0.0.1` with a temporary folder; the test was removed afterwards. `serveBook` does not check the extension of the file it opens, and the entry's `format` comes from the same file (read from the code, not tested).

**Why it matters:** the catalog is a file that can be edited by hand, synced from another machine or unpacked from an archive, and a person can share a folder they did not build. Sharing is offered on the local network and can be started with no authentication (ADR 0018).

**Impact:** reading any file the app's user can read, by someone who controls the catalog of a shared folder and can reach the server.

**Priority:** High. The fix is small.

**Direction:** reject `..`, absolute paths and backslashes in the manifest schema, and in `serveBook` check with `path.relative` that the resolved file is still inside the library before opening it. Tests for both.

### 2. Any filesystem `EACCES` is reported as "the sharing server could not be started"

**Where:** `src/main/ipc/result.ts:41-50`.

**Problem:** the OPDS-specific mapping (`EADDRNOTAVAIL` or `EACCES` → `sharing_failed`) lives in the function every handler shares. Running it with an error shaped like a failed `mkdir` (`code: 'EACCES'`) returned `{ code: "sharing_failed", message: "The sharing server could not be started on that network address." }`. `workflow:plan` reaches this through `pendingRuns.prepare()`, which creates the pending folder, and any other file-system call that is not wrapped first can too.

**Why it matters:** the person is told to look at the network when the problem is a folder's permissions, and a bug report would carry the wrong code.

**Impact:** a misleading message on a rare but real path.

**Priority:** Medium.

**Direction:** keep the sharing mapping in the OPDS handlers, or narrow it (`syscall === 'listen'`); give file errors their own message.

### 3. Unexpected errors leave no trace

**Where:** the fallback of `toFailure` in `src/main/ipc/result.ts`.

**Problem:** an error the function does not recognise becomes `{ code: 'internal_error', message: 'Mangabound could not complete that action.' }` and is not logged. The six `console.error` calls in `src/main/ipc` are each in a handler for one best-effort step (remembering a folder, publishing to the catalog, recovering or deleting pending books); none is in the fallback. A `TypeError` thrown by a bug looks the same to the person, and to whoever reads the log, as any other failure. The function also decides by an `instanceof` chain over six error classes (`ToolExecutionError`, `ConversionWorkflowError`, `MetadataProviderError`, `LibraryIndexError`, `SettingsSaveError`, `CliProtocolError`), each with its own union of codes.

**Why it matters:** the most useful report a person can send, "it said it could not complete that action", cannot be traced.

**Impact:** slower diagnosis of every real bug.

**Priority:** Medium.

**Direction:** log the error and its stack in the fallback. A small common base for the six classes (a `code` and a message safe to show) would replace the chain.

### 4. "Write to a temporary file, then rename" exists four times, and three of them lack the retry the project already wrote

**Where:** `src/adapters/library/fs-library-store.ts:73`, `src/adapters/library/fs-pending-runs.ts:123`, `src/adapters/mangabind/binding-port.ts:56` and `src/adapters/settings/fs-settings-store.ts:78`.

**Problem:** the four differ in the name of the temporary file (`createTempSuffix`, `randomUUID`, process id plus `randomUUID`), in whether the temporary file is removed when the write fails, and in whether the rename is retried. Only the settings store (and the book store, which is not one of the four) uses `renameWithRetry`, whose comment describes exactly the case at hand: on Windows a rename fails with `EBUSY`, `EPERM` or `EACCES` while an antivirus scanner or an indexer holds the file. The catalog (`.mangabound/library.json`, in the person's own library folder), `pending.json` and the `mangabind.json` written by the binding port use a plain `rename`, and the catalog store also leaves its `.tmp` file behind when the write fails (the other three clean up).

**Why it matters:** the catalog is what the "the book was copied, but its destination catalog could not be updated" warning is about, and it is written into a folder that antivirus and sync tools watch. A real lock was not reproduced here; the finding rests on the helper's own documented reason for existing.

**Impact:** an occasional, hard-to-explain warning after a save, and stray `.tmp` files in a folder the person owns.

**Priority:** Medium.

**Direction:** one `writeFileAtomically` in `src/adapters/fs` (exclusive temporary name, retried rename, cleanup on failure) used by all four. The adapters are under the 100% gate, so the change is well covered.

### 5. Logic in `pending.ts` that the gate cannot see, twice over

**Where:** `src/main/ipc/pending.ts` (`pending:save-all`, `saveFailure`).

**Problem:** the loop that names each book of a save-all (`Name.epub`, then `(2)` up to `(999)`, retrying on `EEXIST`) is a second algorithm for what `uniqueFileName` in `src/library/unique-name.ts` does for the staging folder. The helper came with ADR 0029 and the loop was left as it was; they differ in how a name counts as taken (the helper leaves that to its caller, the loop asks the file system) and in the limit (none, against 999). `saveFailure` tells its own messages apart from system errors by testing `error.message.startsWith('Choose a ')` and `startsWith('This pending book')`.

**Why it matters:** both live in `src/main`, which no unit test reaches, and matching on message text breaks silently when a sentence is edited.

**Impact:** two file-naming rules that can drift, and an error path that a copy edit can change.

**Priority:** Low to medium.

**Direction:** move the save-all naming and the classification into a unit under the gate, use the existing helper, and give the errors codes.

## Findings — architecture and responsibilities

### 6. `App` runs the conversions, and it grows with every feature

**Where:** `src/renderer/app.tsx`.

**Problem:** the file has 1,520 lines. The `App` function alone is 1,256 lines with 216 branches, 31 `useState` calls and a reducer. It was 679 lines on 2026-09-14, 1,139 when the previous audit was written, 1,330 on 09-28 and 1,520 today, and 11 of its 31 commits are from the week since that audit. `startRun` (`app.tsx:599`, 162 lines, 39 branches) is not wiring: it decides which rows leave the queue, which ones are reported as skipped and whether they can be fixed, and how each library title's outcome is told. Around it:

- Navigation is three pieces of state (`step`, `editingId`, `editingTitle`) with four editing steps (`editing`, `editing-title`, `details`, `details-title`): the two mapping steps repeat a back button and a `MappingEditor`, the two details steps repeat a `BookDetailsScreen`.
- The options page is inline JSX inside `App`, with a focus effect that exists only because it is inline (its comment says so).
- Nine `if` guards (`bridge?.loadSettings === undefined`, `bridge.openArtifact !== undefined` and so on, lines 259-1417) test methods that `MangaboundBridge` declares as always present. They can never be true in the app, TypeScript does not object, and ESLint's `no-unnecessary-condition` is not enabled.
- The conversion progress is state of `App`.

**Why it matters:** the earlier audit left the state sprawl alone because no concrete pain justified it, and said restructuring the most exercised component on spec alone was a risk. The pain is now concrete: the rules that decide what a run leaves in the queue can only be tested through `tests/component/workflow-app.test.tsx` (3,507 lines), and `src/renderer` is outside the coverage gate.

**Impact:** each feature adds 80 to 100 lines to a single function, and a change to the run's rules is verified only end to end.

**Priority:** High.

**Direction, in order:** (a) move the decisions of `startRun` (what is skipped and why, which rows leave, the result of each title) into pure functions in the domain, under the gate; (b) replace `step`, `editingId` and `editingTitle` with one discriminated union; (c) make the options page its own screen and pull the settings, sharing and pending-run effects into hooks; (d) drop the nine dead guards and turn the lint rule on; (e) see finding 16 for the progress. A state library is not part of this.

### 7. `SingleInputWorkflow` is the whole application layer

**Where:** `src/application/workflows/single-input.ts` (917 lines, 15 commits, 8 of them in the last week).

**Problem:** despite its name it also reads libraries, keeps the sessions, persists details, plans, schedules a pool of conversions and aggregates their progress. Within it:

- The preconditions of a run (valid settings, session found, not a library, mode supported, single-book requirements) are written out three times: `convert` (167-205), `plan` (294-332) and `convertLibrary` (461-483).
- The "This input is no longer available" error is built in four places (180, 307, 409, 840) and "No volume files were produced" in four (240, 247, 519, 557).
- `produceVolumes` (148 lines) mixes the worker pool with progress aggregation and hands its result back by filling an array it is given.
- `convertLibrary` has two near-identical per-title branches, one for a single book and one for volumes.

**Why it matters:** the file is where the most product rules land, and each new rule must be remembered in three preambles.

**Impact:** a rule added to `convert` and forgotten in `plan` gives a plan that says yes to a run that will fail.

**Priority:** Medium to high. This is also the safest place to refactor: it is under the 100% gate and has 2,439 lines of tests.

**Direction:** a shared `assertRunnable` and `requireSession`; the volume pool as its own module returning its artifacts; then split by responsibility (sessions, a single run, a library run) behind the same public methods, and rename.

### 8. The IPC layer repeats itself, and is outside the gate

**Where:** `src/main/ipc/*` (30 handlers in about 1,300 lines) and `src/main/context.ts`.

**Problem:** every handler repeats `try`, schema `parse`, `catch` and `failed(toFailure(error))`. `workflow:convert` and `workflow:convert-library` share about 35 lines (find the library, refuse while it is being deleted, refuse a job id in use, create the controller, track artifacts, clean up in `finally`), and the request-to-workflow mapping (`...(command.x === undefined ? {} : { x })`) is written out three times. `MainContext` is a bag of mutable fields: six `| undefined`, and five maps from ids to paths (`selectedInputs`, `selectedLibraries`, `artifactPaths`, `pendingArtifacts`, `activeJobs`) changed from three files. The rule for remembering the last folder and rewriting the preferences appears twice (`rememberPickerFolder` in `inputs.ts`, `rememberFolder` in `pending.ts`) over three shared mutable fields.

**Why it matters:** this is where findings 2, 3 and 5 come from, and it has no unit tests: its only check is the packaged end-to-end run.

**Impact:** an inconsistency in how one handler treats errors is found by reading, not by a test.

**Priority:** Medium.

**Direction:** a `handle(channel, schema, run)` that parses, catches, logs and maps; a `runJob()` for the controller lifecycle; and the logic that does not need Electron moved out of the handlers so the gate reaches it.

### 9. The bridge is described four times, and nothing ties the copies together

**Where:** `src/shared/workflow-contract.ts` (the schemas), `src/shared/runtime-info.ts` (the type), `src/preload/index.ts` (the channel name and a generic `invoke<T>`) and each `ipcMain.handle('…')`.

**Problem:** the return type at each preload call is a cast (`ipcRenderer.invoke(...) as Promise<WorkflowResult<T>>`), and the channel is a string typed twice, once in the preload and once in the handler. Adding one command touches four files, and `workflow-contract.ts` has had 19 commits.

**Why it matters:** a handler that starts returning a different shape compiles, and the page finds out when it runs.

**Impact:** drift between the two sides of the window that no compiler or test flags.

**Priority:** Medium.

**Direction:** one map of channels to `{ request, response }` from which the preload and `handle` are derived. Do it after finding 8's helper.

### 10. `MappingEditor` is one 726-line function, and passes a value nobody uses

**Where:** `src/renderer/components/mapping/mapping-editor.tsx:103`.

**Problem:** 10 `useState` calls and 64 branches in one component that draws the header, the history buttons, the chapter table and the volume table. `onConfirm(metadata, draft)` serializes the mapping to JSON as its first argument; both callers in `app.tsx` (lines 1247 and 1305) name it `_metadata` and ignore it, and the adapter serializes the mapping again itself. The component tests assert on the ignored value.

**Why it matters:** it is the second-largest component and the one that has changed the most after `App` (13 commits), and part of what it does is dead.

**Impact:** modest today; it grows the next time the mapping flow changes.

**Priority:** Low to medium.

**Direction:** drop the first argument and its tests; split the header, toolbar and tables when the file is next touched. `MangapressSettingsEditor` (487 lines) is long but flat, a form of 26 fields, and has caused no trouble.

## Findings — consistency, duplication and dead code

### 11. Dead code and dead guards

**Where and what:**

- `src/shared/job-status.ts` is imported by nothing, and `src/shared/README.md` still lists it.
- `inputKindSchema` (`src/shared/workflow-contract.ts:47`) and the `OutputProfile` interface (`src/domain/output-profile.ts:52`) are declared and never used.
- The `Foundation` screen in `app.tsx`, shown only when there is no bridge, still carries the first milestone's copy ("Architecture checkpoint"). The bridge always exists in the app.

**Why it matters:** each of these invites a reader to wonder what uses it, and the guards hide a removed bridge method instead of failing.

**Priority:** Low. These are quick wins.

**Direction:** delete them, and turn on `@typescript-eslint/no-unnecessary-condition`; expect it to find more.

### 12. The same idea is typed more than once, and one domain module knows a tool's file format

**Where:** `src/domain/conversion.ts`, `src/domain/input-queue.ts`, `src/shared/workflow-contract.ts`, `src/domain/mapping.ts`.

**Problem:**

- `'folder' | 'cbz'` is defined as `InputKind` and as `QueueInputKind`; `InspectedKind` and `QueueRowKind` are the same union with `'library'`.
- One title of a library is `InspectedTitle`, `LibraryTitle` and `ReadTitle`, and `LibraryTitleSummary` in the contract, translated by hand between them.
- `conversion.ts` imports `MangapressSettings` from `output-profile.ts`, which imports `BookFormat` back: the one cycle in the graph.
- `domain/mapping.ts` exports `MangabindMetadataFile` and `toMangabindMetadata`, the shape of mangabind's own file. Only the adapter and the ignored argument of finding 10 use them.
- `output-profile.ts` holds the mangapress settings, not an output profile.

**Priority:** Low.

**Direction:** define each union once and re-export it; move `BookFormat` to a file of its own to break the cycle; move the mangabind file shape into `adapters/mangabind` with finding 10.

### 13. A form-field component exists, but only inside one file

**Where:** `TextField`, `SelectField` and `SettingsSection` at the bottom of `src/renderer/components/settings/mangapress-settings.tsx`.

**Problem:** the details page (`book-details-screen.tsx`) and `MappingEditor` build their own label, input and message by hand. The earlier audit's repeated row-item pattern (its item 7) is still open for the same reason.

**Priority:** Low.

**Direction:** move the fields to `components/shared` when the next form is built.

## Findings — tests

### 14. The 100% gate covers 43% of the source, and the problems above are outside it

**Where:** `vitest.config.ts` (the `coverage.include` list).

**Problem:** the gate covers `domain`, `application`, `adapters`, `library`, `opds` and `renderer/lib`: about 6,700 of 15,700 lines. Outside it are `renderer` (6,649 lines, of which `lib` is 29), `main` (1,620), `shared` (554) and `preload` (140). `startRun`, the save-all naming, `toFailure` and the handlers are all in the second group. ### 15. Very large test files, and casts to fake `fs`

**Where:** `tests/component/workflow-app.test.tsx` (3,507 lines, 103 tests, ten `describe` blocks, its own `bridge()` builder at line 92), `tests/unit/single-input-workflow.test.ts` (2,439), `tests/unit/binding-port.test.ts` (1,070); `as unknown as` in `fs-library-store.test.ts` (16) and `fs-settings-store.test.ts` (13).

**Priority:** Low to medium.

**Direction:** split the component test by `describe` around a shared `tests/component/support/bridge.ts` (mechanical, no behavior change); the two unit files follow finding 7. Inject narrow interfaces instead of `typeof readFile`.

## Findings — performance (not measured)

### 16. Progress events are not throttled and re-render the root component

**Where:** `src/main/ipc/conversion.ts` (`event.sender.send('workflow:progress', …)`), `setProgress` in `src/renderer/app.tsx`.

**Problem:** nothing in `src` throttles or debounces (the only timers are the rename retries). mangapress reports page events (`MangapressPageEvent`) and mangabind reports page counts, and each update for the running job reaches `setProgress` in `App`, which re-renders the 1,256-line function and recomputes `planKey`, a `JSON.stringify` of the whole queue with a mapping signature per row (`app.tsx:542`), on every render. For a few volumes this is unnoticeable; for a library of dozens of titles the number of renders is in the tens of thousands. No measurement was made.

**Priority:** Low to medium; measure with a large library before acting.

**Direction:** move the subscription into `RunningScreen`, so a progress event re-renders that screen only. It also removes state from `App` (finding 6).

Also noted, and fine at today's sizes: `pending:list` finds each book's id by scanning the whole `pendingArtifacts` map, and each OPDS request re-reads the catalog and may list the folder (`scanUntracked`).

## Answers to the questions this audit was asked

- **Is a broad refactoring worth it now, or only spot fixes?** Neither extreme. Phase 0 is spot fixes and should go in regardless. Phases 1 and 2 are a bounded round on three files (`app.tsx`, `single-input.ts`, `src/main/ipc`) and are worth doing before the next large feature, because those files are where each feature currently adds its cost. A rewrite is not.
- **Main technical debts:** `App` as the orchestrator (6); `SingleInputWorkflow` as the whole application layer (7); an IPC layer with no shared handling and no tests (8); the bridge described four times (9); four atomic writes (4).
- **First:** finding 1 (security), then 2 and 3 (small, and they improve every later bug report), then 6a.
- **Independent of each other:** everything in Phase 0, finding 4, and the pieces of finding 7.
- **Highest regression risk:** finding 6, because `App` is outside the gate and only component and end-to-end tests stand behind it; finding 9, because it touches every channel; finding 8, because uniform error handling changes messages that the end-to-end tests read; finding 4, because the Windows locks it is for are hard to reproduce.
- **Better left alone for now:** a state library for `App`; `MangapressSettingsEditor`; the `queueReducer` and `domain/mapping.ts`, which are large but pure, covered and stable (four commits for the reducer); `binding-port.ts` apart from finding 4; and any move or rename made for looks only.

## Addendum — 2026-09-30

Finding 1 has been fixed. The catalog's reader now refuses an entry whose path is not below the library (`isLibraryRelativePath`, used by the manifest schema), and the OPDS server resolves each entry with `resolveLibraryFile` before it opens anything, so the `../outside-secret.epub` catalog that answered 200 now answers 404 through a store that returns it as it is, and is refused as unreadable by the real one. Both cases have a test that fails without the change. Symlinks inside a library are not followed or checked any differently than before: a library laid out with links to other disks keeps working, and that was left alone on purpose.

Findings 2 and 3 have been fixed as well. The mapping of the sharing server's errors (`EADDRINUSE`, `EADDRNOTAVAIL`, `EACCES`) moved out of `toFailure` into `src/main/ipc/sharing-failure.ts`, and `opds:start-sharing` applies it only to the call that starts the server. A file-system `EACCES`, `EPERM` or `EROFS` now says that a file or folder could not be used (`file_access_denied`), `ENOSPC` says the drive is full (`disk_full`), and neither mentions the network. Every branch of `toFailure` that replaces an error with a message of its own, and every error that carries a `cause`, now logs the real error with `console.error`, and so does the catalog read that precedes sharing; the fallback `internal_error` logs the error and its stack. `tests/unit/to-failure.test.ts` covers each branch, and 13 of its 21 tests fail against the previous function. What remains of finding 3: the log is the console, not a file, so a person who starts the app from the desktop still has nothing to send, and the six error classes are still told apart by an `instanceof` chain.

Finding 11 has been done, except for the `Foundation` screen. `src/shared/job-status.ts`, `inputKindSchema` and the `OutputProfile` interface are gone, and so are the nine `if` guards on methods of the bridge in `app.tsx`. Those guards were load-bearing for one thing: `tests/component/app.test.tsx` gave the app a bridge with two methods, so the guards kept it from calling the rest. The test now uses a complete, inert bridge (`tests/component/support/bridge.ts`), which the split of `workflow-app.test.tsx` can build on. `@typescript-eslint/no-unnecessary-condition` is on for every TypeScript file, and the repository passed it after 17 findings. Four were guards of the kind above; `bridge?.loadSettings === undefined` and its like were not among them, because the optional chain makes the comparison look possible, so those were found by reading. Three were the compiler taking a flag set from inside a callback for unchanged (twice in `single-input.ts`, once in the effect in `app.tsx`), which were restructured rather than silenced. Two were dead fallbacks that Electron's own typings make unreachable (`pending.ts`), and seven were stories, tests and an end-to-end helper reading a value the type already guarantees, or guarding against an environment the types do not know about (jsdom has no `ResizeObserver`). One was a real bug: `parseMangapressEventLine` looked an event's `type` up in a plain object, so a type such as `constructor` or `toString` found a method of every object and failed with a `TypeError` instead of being treated as an unknown event; it now looks at own properties only, with a test that fails without the change. The `Foundation` screen stays: it is what the page shows with no desktop shell behind it, and a story, two tests and the title bar's label depend on it, so removing it means deciding what that case should show.

Finding 15 has been done for the component test. `tests/component/workflow-app.test.tsx` (3,507 lines) is now six files by topic (`workflow-queue`, `workflow-options`, `workflow-process-control`, `workflow-sharing`, `workflow-libraries` and `workflow-book-details`, between 300 and 1,000 lines each) and two support modules (`support/workflow.ts` for the fake bridge and the fixtures, `support/library.ts` for the library ones). Nothing was rewritten: every non-blank line of the old file is in the new ones exactly as many times as before (checked mechanically, ignoring imports, the `afterEach` each file repeats and `export`), and the project still runs 291 component tests. The suite also runs faster, since the files run in parallel: about 13 seconds locally, against about 49. The two large unit files (`single-input-workflow.test.ts`, `binding-port.test.ts`) and the casts in the file-system tests are left for the changes to the code they test.

## Addendum — shared atomic writes (2026-09-30)

Finding 4 is addressed by `src/adapters/fs/write-file-atomically.ts`, used by the library catalog, pending-run saved-state record, settings store, and binding adapter's metadata writer. Each writes to an exclusive UTF-8 temporary file beside the destination and publishes through the existing `renameWithRetry`; a failed write or rename triggers cleanup.
