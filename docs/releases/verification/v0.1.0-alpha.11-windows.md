# Published-package verification: v0.1.0-alpha.11

Verified on **2026-10-07**. This is a post-publication check of downloaded assets, not a local rebuild or a claim that every desktop release check is complete.

## Release and environment

- [Public release](https://github.com/gustavommcv/mangabound/releases/tag/v0.1.0-alpha.11), published on 2026-10-05.
- Tagged source: `dfd727c1537b34fb6313ab80e4bb8ba989f7cc36`. The [Release run](https://github.com/gustavommcv/mangabound/actions/runs/37261422155) for that exact commit completed successfully; this is build evidence, separate from the checks below.
- The same tagged commit's push runs for [application CI](https://github.com/gustavommcv/mangabound/actions/runs/37261036334) and [Documentation](https://github.com/gustavommcv/mangabound/actions/runs/37261036145) also completed successfully. Their results were rechecked remotely, not inferred from the release run or a different commit.
- Windows 11 Pro, version `10.0.26300`, x64. The test process ran at medium integrity, without elevation.
- The unmodified public portable ZIP contains Mangabound `0.1.0-alpha.11` and Electron `44.4.5`. The current checkout was not used to rebuild it.
- Bundled tools: mangabind `v0.6.1` and mangapress `v0.7.2`. Both executable hashes matched the shipped manifest and the release's locked pins. The executable's fuse settings matched the project's security configuration; no inspector, test bridge, or `--no-sandbox` switch was enabled.

All seven public assets were downloaded into a new temporary test directory. The portable ZIP was extracted there. A separate user-data directory and the supported absolute pending-book/cover roots isolated the run from the installed app and its books. `APPDATA`, `LOCALAPPDATA`, `TEMP`, and `TMP` also pointed into that test directory. This tests the released workflow, not migration of the default storage directories or installer integration.

Inputs were copies of the committed procedural-image fixtures described in [the fixture README](../../../tests/fixtures/e2e/README.md). They are unchanged between the release tag and the checkout used for this verification. The input copies, not the repository fixtures or personal manga, received any generated metadata.

### Linux package permission listings

The downloaded Linux packages were also inspected without installing or executing them. Windows' libarchive/bsdtar `3.8.8` listed the RPM and Arch payloads and the DEB's `data.tar.zst`; those listings were passed to the existing [package-permission checker](../../../scripts/verify-package-permissions.mjs), not a second implementation of its rules.

| Published package | Entries checked | Result |
| ----------------- | --------------: | ------ |
| DEB               |              95 | Pass   |
| RPM               |             100 | Pass   |
| Arch              |              93 | Pass   |

The checker found no entry with permissions that prevent a non-owner from reading a file, entering a directory, or executing a program that its owner can execute. This checks the permission metadata of the actual downloads; it does **not** establish package installation, sandbox behavior, dependency availability, or working conversions on Linux.

## Windows portable workflow results

All application interactions used the released GUI and actual Windows file dialogs, without dialog mocks or renderer instrumentation. File inspection used standard ZIP/XML readers and SHA-256 hashing; HTTP checks used the actual server started from the Share panel.

| Check                              | Observed result                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Extract and launch                 | The portable executable opened with a fresh queue and defaults, without installing the app or requesting elevation.                                                                                                                                                                                                                      |
| Chapter folder through both tools  | `manga-named-volumes/Named Volumes` appeared as three chapters grouped into two volumes. Processing without choosing an output location produced two ready EPUBs.                                                                                                                                                                        |
| EPUB contents                      | Volume 1 contains the first and second chapters, in that order; volume 2 contains the third. Their `toc.ncx` labels and targets agree with that grouping. `container.xml`, OPF, NCX, and XHTML entries parsed as XML, and the EPUB MIME entry is correct. This is not an EPUBCheck conformance run or a physical-reader rendering check. |
| Share before saving                | Sharing the ready books on the chosen Ethernet interface returned HTTP 200 navigation and acquisition feeds with the corresponding OPDS MIME types. Both books appeared newest-first by their recorded conversion timestamps. Each acquisition returned `application/epub+zip` and a byte-identical copy of its pending EPUB.            |

## Still pending

- Windows installer: SmartScreen wording and installer launch, Start Menu shortcut, install/upgrade/uninstall, and survival of unsaved books in the default storage location. CLI downloads and this isolated portable run do not establish browser-download security-prompt behavior. The installer was downloaded and hashed, not installed over the owner's existing app.
- macOS arm64: opening the downloaded ZIP on macOS, Gatekeeper behavior, and a real conversion. Only download integrity was checked here.
- Linux `.deb`, `.rpm`, and Arch package: native installation, launch, and real conversion as a normal user for each. Download integrity and permission listings were checked here, not native execution; passing those checks or Windows conversions cannot establish Linux runtime or sandbox behavior.
- Other checks in [the desktop release checklist](../../release-checklist.md), including native drag-and-drop, scaling, accessibility with a screen reader, file associations, removable-drive interruption, and physical-reader acquisition/rendering.

No application fix or new release tag was needed for the verified flows. This record is a partial release-hardening result, not approval of the outstanding checks.
