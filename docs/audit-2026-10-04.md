# Five heavy audit passes (2026-10-02), and what has been done about them

- Date of the passes: 2026-10-02. Recorded here: 2026-10-04.
- Commit audited: `677052e` (`main`, after `v0.1.0-alpha.10`).
- Method: five passes, each given one area and one brief, run by Claude Opus on a Linux x64 machine with no access to the GitHub API. They read the code and then reproduced what they claim: they ran the real pinned tools, built the real `.deb`, mounted a real FAT file system, drove the packaged app, and mutated the code by hand (191 mutants against the unit suite). Anything that depends on Windows or macOS is marked as unverified in the reports.
- Passes: 1, trust boundaries and the desktop shell; 2, correctness of the core (mapping, queue, workflows, binding); 3, release, CI and supply chain; 4, whether the tests protect what they say they protect; 5, the renderer.

This is a record, not a plan. It lists every finding with its severity and its present status, and it is updated as the findings are dealt with. The reports themselves are not in the repository; each finding below keeps its ID (`P<pass>-<number>`) so a commit or a pull request can refer to it.

**Before any of it was accepted,** the findings that decide what to do first were reproduced here, on Windows, on the code they were written against: the packaged window can load local files (the `GrantFileProtocolExtraPrivileges` fuse is on), "Stop sharing" waits forever on a stalled download, a 260-character title fails on NTFS only after the whole conversion, a duplicate chapter is dropped without a word by the real `mangabind`, the pending books live inside Squirrel's install root, the end-to-end specs leave 351 folders (about 700 MB) in the temporary folder, and the two sandbox scripts exit 0 on every path.

**Statuses:** _fixed_ names the pull request; _open_ means nothing has been done; _upstream_ means the cause is in another repository.

### P1-01, P1-05 and P1-06: the window

**What was found.** The packaged page was loaded from `file://`, which Electron gives extra privileges by default, so code in the page could read any file the person can, and a CSP that allowed `ws:` and `wss:` let it send what it read to any host. Every permission request was granted (microphone, location, notifications), and starting to share accepted any address the page named, `0.0.0.0` included.

**What was done** ([ADR 0041](adr/0041-the-window-loads-its-page-from-its-own-scheme.md)).

- The fuse `GrantFileProtocolExtraPrivileges` is off. Switching it off alone leaves a window that never loads (Electron cannot read a page from inside `app.asar` over `file://` then; shown by flipping the fuse in the packaged binary), so the packaged page is served from its own `app://mangabound` scheme.
- The page's `connect-src` is `'self'`; the development server's own socket is the same origin as its page, which `'self'` covers (checked in Chromium).
- The request, check and device permission handlers refuse everything except the clipboard write the Copy button needs.
- Sharing starts only on an address the device has now, or on loopback; the check lives in the network adapter, under the unit gate.
- `tests/e2e/window-policy.e2e.ts` runs the attacks against the packaged app: reading a file, opening a socket and a request to a listener the test owns, asking for notifications and the location and querying the microphone, camera and clipboard permissions, sharing on `0.0.0.0`, `::`, `localhost` and an address the device does not have. All four tests fail on a build with the four protections taken out.

**Not done.** P1-10 and P1-11 (the smaller trust assumptions of the shell) and P4-02 (the decisions in `src/main` named by the audit that no test protects) are separate findings and stay open.

### P1-03 and P4-03: stopping to share

**What was found.** `server.close()` answers only when every connection has ended, and nothing ended a response whose reader had stopped reading. "Stop sharing" waited for ever, the sharing state stayed set, and quitting left the process running with no window. The same download left its file open when the reader simply went away, because the file was piped to the response with `pipe`. Three mutants of the authentication (a blank username opening a share that has a password, the navigation feed answered without credentials, the `Basic ` prefix not required) survived the tests.

**What was done.**

- Stopping closes every open connection, so the downloads in progress end and the stop answers at once.
- A connection that does nothing for a minute is closed (`server.timeout`), which is what ends the connection of a reader that fell asleep.
- The file is sent with `pipeline`, so a reader that leaves closes it; leaving halfway is not logged, any other failure is. A failed read now cuts the connection instead of finishing a book that is cut short with an error text.
- An entry of the catalog that is not a file is answered with 404.
- Tests run the real server against a real socket that stops reading (a 64 MiB book): stopping resolves and the reader's connection ends, an idle reader is dropped, the file is closed when the reader leaves, and a failing read is cut and logged. Each was checked by undoing its protection. The authentication gaps have their tests.

**Not done.** Bounding the wait in `before-quit` for the other things it waits on (the workflow, the settings write) is not part of this finding.

### P1-07 and P1-09: what the page may send

**What was found.** A title of 260 characters or of 90 Japanese characters was accepted and converted page by page before `mangapress` failed to write its file, because a file name holds a limited number of bytes (reproduced with the real tool). The command contracts had no ceiling on any string or list, so a payload of 200 thousand chapters and a title of five million characters was taken in a fifth of a second, and a NUL in a title or an author, which a looked-up author name could carry, became a generic internal error with only a log line.

**What was done** ([ADR 0030](adr/0030-title-author-and-language-belong-to-each-book.md), amendment).

- A title is limited to 200 bytes of UTF-8, in the field (it stops at a whole character and says so), in the contract and where the details are kept. Control characters become spaces where details are kept and are refused by the contract. A real `mangapress` converted a title of 200 letters and one of 66 Japanese letters, each with ` - Vol.01`, and failed on 260 letters, as the audit found.
- Every string and list in the workflow, sharing and settings contracts has a ceiling well above what a real folder holds (the longest series has about 1,200 chapters): 20,000 chapters, 5,000 volumes, 1,024 characters for a name, 4,096 for a path, 64 for a source, 64 for an interface address.

**Not done.** A title that is a reserved device name on Windows (`CON`) is not refused. Contracts that only carry the identifiers the app itself made (a session, a library) were already bounded at 200.

### P2-01: two copies of a chapter

**What was found.** A folder often holds the same chapter twice, from two groups. `mangabind` skips every copy, and `mangabind.json` can only say "chapter 2", so placing one copy in a volume in the editor changed nothing: the book shipped without the chapter, and the run ended with "2 books saved." The audit reproduced it with the pinned `mangabind`.

**What was done** ([ADR 0039](adr/0039-mangapress-warnings-are-shown-with-the-results.md), amendment).

- The editor and the main process refuse a draft that places one of two copies of a chapter, with a message that says to remove all but one from the folder. Copies that the file names put in different volumes are left alone. Checked against the real `mangabind` on the audit's folder.
- What the joining step reports as left out (`chapter_conflict`, `chapter_gap`, `empty_chapter`) is now told with the books of a run, for a folder and for a library, instead of being dropped.

**Not done.** `mangabind.json` still cannot name one copy of a chapter, so the choice cannot be made inside the app. Naming a chapter by its folder would take a change in `mangabind`.

### P2-03, P2-04, P2-07 and P2-09: what the app does with the person's files and names

**What was found.**

- **P2-03.** Saving to a FAT or exFAT drive (a Kindle or Kobo over USB, an SD card) staged a copy beside the destination and, since those systems cannot make hard links, copied it again to the final name before removing the staged one. Both copies existed for a moment, so a book that fit was refused as "the destination is full" when the free space was between one and two book sizes (reproduced by the audit on a real FAT image).
- **P2-04.** Saving a mapping rewrote the person's `mangabind.json` and carried over only the author and language. A `source`, a note on a volume, keys of the person's own or of another tool were gone the first time the volumes were edited, although the code's own comments said every other key was kept. A file that was not valid JSON was overwritten without a word.
- **P2-07.** The validated plan listed the CBZ names `mangabind` joins (`Named Volumes - Vol.01.cbz`) for a run that makes `My Title - Vol.01.epub`: another title, another extension.
- **P2-09 (three of the four).** A book whose name differs from one in the library only in how an accent is written (`é` as one character or two, the same name on APFS) could replace it. One MangaDex volume called `+1`, `-1` or `0x10` made the app refuse every volume of the work. Cancelling between two titles of a library left the rest without an outcome, so the results could not say the run was cancelled.

**What was done.**

- The staged copy is removed before the book is copied to its name when a hard link is not possible: at most one copy is on the drive at a time. The copy is still exclusive, so a book already there is never replaced.
- The mapping is laid over the file it replaces: the volumes and their chapters, the title and the source when the mapping names one are replaced, and every other key is kept in the order the file had it, including the keys of a volume that is still there. A file that is not a JSON object is refused instead of overwritten, and the error says to check that it is valid. Checked against the real `mangabind`, which read the merged file and bound the volumes.
- The plan names the books the run makes: the typed title and the volume's number, else the file's name, and the extension of the format chosen. A run that stops after joining still says its CBZ files.
- Names are compared after normalizing accents; MangaDex volumes are filtered with the pattern the editor accepts; a cancelled library run reports each title it did not reach as cancelled.

**Not done.** Integers above 2^53 in a `mangabind.json` still change when the file is rewritten, and a Kobo's `.kepub.epub` is planned as `.epub`. A volume number of `10000000000000000000000` is still written as `1e+22` (the fourth of P2-09). P2-02 (a run of one title binds every title of the library first) and P2-05 (chapter folders `mangabind` cannot parse are left out of the editor) are not in this part.

### P2-05: folders mangabind cannot read as chapters

**What was found.** A folder whose name `mangabind` cannot read as a chapter (`Omake`, `Ch.004 [GroupA]`, `Ch.006 (en)`, `第11話`) never became a chapter of the draft, so the editor could not show it and the books were made without it. The issues listed it as `unparsed_chapter`, but the issues were dropped on the way to the queue, and the row counted only the parsed chapters.

**What was done.** The names of such folders are taken from what `mangabind` reported (checked against the real tool, which names all four of the examples above) and travel with the inspected folder. The row's note says which folders are left out and what to do, and the mapping editor shows the same under **Folders left out**: the app cannot place a folder whose chapter it does not know, so the fix is to rename it to include a chapter number and add the folder again. The user guide (EN and PT) says so.

**Not done.** Libraries: the titles of a library read by `mangabind --batch` carry the same issues, but the library screen does not show them yet. Teaching `mangabind` the common forms (`[Group]` and `(lang)` without a title, `Extra`, `Omake`), which the audit also suggests, is a change in `mangabind`.

### P2-06 and P2-08: the numbers in the options, and the settings file

**What was found.** `mangapress` takes any number for the options a typo can ruin: a gamma of 18 for 1.8 made every page almost black and the run ended as a success; a cropping power of 50, or a width of `1e21`, got as far as the tool. And one saved value out of range made the app discard the whole settings file, with every other option and both remembered folders, behind a single generic notice. That made any later tightening of a range costly for everyone with an old value in their file.

**What was done.**

- Bounds, kept in the domain and used by the contract and the settings file alike: gamma 0.1 to 4 (below 0.1 the tool means "the device's own", which is leaving it empty), cropping power 0 to 10, a custom size 1 to 20,000 pixels. They are wide: they refuse a slip of a key, not a choice. The options page names the range in its message.
- The settings file is read field by field. A value of the wrong kind or out of range goes back to its default and the rest is kept; the notice names what was reset ("Some saved options could not be used and are back to their defaults: gamma."). A file that is not JSON, not an object or from another version is still discarded as a whole, and an option the file lacks takes its default without a notice.

**Not done.** The bounds are the audit's suggestions made concrete, not read from KCC: the ranges KCC's own window allows were not checked against it.

### P3-04, P3-05 and P3-07: what the release path says it checks

**What was found.** The documentation of `toolchain:update` and the pull-request text it writes said the tools' handshakes are run; no executable is run in that step, and the protocol version it writes is a constant. Nothing at build time checked that the pinned tools' output still parses with the app's parsers: `capabilities:check` reads the names of flags, and the protocol fixtures were written from earlier builds. The alpha.10 notes understated the check at start-up. The publish job kept its write token in `.git/config`, and there was no procedure for withdrawing a bad real release.

**What was done.**

- The texts say what the step does and where the handshake is checked (`CONTRIBUTING.md`, the pull-request body, the alpha.10 notes).
- `tests/unit/pinned-tools-output.test.ts` runs the real pinned tools (a plan and a library with `mangabind`; a plan, a conversion and the list of devices with `mangapress`) and reads everything they print with the app's own parsers, so a tool update that keeps its flags and changes its JSON fails the unit suite, which the release does not run but every pull request does.
- The publish checkout does not persist credentials, and `RELEASING.md` has a procedure for withdrawing a real release.

**Not done.** P3-06 (floating runner images, a rolling Arch container, unpinned system packages, development install scripts run in the release job) and the remaining items of P3-07 (a tag ruleset, a draft left by a failed upload, trust on first use of the pins, build provenance) are decisions about the repository's settings and the supply chain that are the owner's.

### P3-02: pending books and covers inside the installer's folder

**What was found.** On Windows the pending books and the covers lived in `%LOCALAPPDATA%\Mangabound`, which is the folder Squirrel installs the app to (Windows takes `Mangabound` and `mangabound` for one name). On the machine used here an install showed `Pending` beside `Update.exe`. Uninstalling removes the folder the installer made, so a person's converted and unsaved books would go with the app.

**What was done** ([ADR 0026](adr/0026-process-then-save-pending-books.md), amendment).

- The two folders are in `%LOCALAPPDATA%\Mangabound Data` on Windows now.
- At start they are moved from the old place, whole or entry by entry, never replacing anything, leaving the installer's files; a failure is logged and the app starts anyway. Checked on the real packaged app against a scratch `LOCALAPPDATA`: the folders and their contents moved, `Update.exe` stayed, nothing was left behind.

**Not done.** The uninstall itself was not run, since that machine has a real install with real data; the removal is Squirrel's documented behavior. The release checklist now asks for it on a clean machine.

### P3-01 and P3-03: the Linux packages

**What was found.** `scripts/acquire-toolchain.mjs` creates the folder for the bundled tools with `mkdtemp`, which makes it readable by its owner alone, and renames it into place. The folder is copied into the installed app with that mode, so on an installed package it is `drwx------ root`. A person who is not root cannot open it, the app's start-up check cannot hash the tools, and every conversion is refused with "Reinstall Mangabound", which cannot help. The pass built the `.deb` from the audited commit and saw exactly that in `dpkg-deb -c`. The `.rpm` and the Arch package take the same folder, and the `PKGBUILD` already carried a comment about this class of problem, fixed for the first two entries only. The first commit of [#146](https://github.com/gustavommcv/mangabound/pull/146), which added only the check, confirmed all three on CI: the `.deb` (1 of 95 entries), the `.rpm` (1 of 100) and the Arch package (1 of 93) each failed on exactly one entry, `resources/toolchain/linux-x64/` as `drwx------ root`.

It went unnoticed because the app opens fine without its tools, the end-to-end specs run the app as the person who built it, and the only Linux package checks were two scripts that report what they saw and always exit 0 (and, since they run only in `ci.yml`, never for a release). The release notes of alpha.10 and `RELEASING.md` described those scripts as checks of the packages.

**What was done.**

- The folder is made readable and enterable by everyone where it is created, and again when a restored CI cache already holds it (`scripts/acquire-toolchain.mjs`). The `PKGBUILD` now sets read on everything in `/opt/mangabound`, and execute on folders and on files that already run, instead of fixing two entries.
- A check that fails the build: `scripts/verify-package-permissions.mjs` reads the listing of a finished package and fails on any folder others cannot open or file they cannot read, or any program only its owner can run. `.github/scripts/check-package-permissions.sh` lists the `.deb` (`dpkg-deb -c`), the `.rpm` (`rpm -qlvp`) and the Arch package (`tar --zstd -tvf`) and runs it. It runs in `make.yml` and `arch-package.yml` on every change and, since those are the files the release workflow reuses, for every release. The first commit of the pull request had only the check, so its failing run is the proof that the check sees the problem.
- `RELEASING.md`, the release checklist and the repository copy of the alpha.10 notes now say what the sandbox scripts are (diagnostics that cannot fail) and ask for a conversion, not only a launch, on each installed package.

**Not done.** The published alpha.10 files have not been listed: the finding is seen on packages CI built from the same packaging code, and expected, not seen, on the published files themselves. The release notes published on GitHub for alpha.10 still carry the sentence the repository copy no longer does, and editing them is the owner's decision. The audit's stronger suggestion, installing the package and running the app's own start-up verification as a non-root user, is not built; the listing check covers the cause that was found, not every way the tools could become unreachable.

### Pass 4: what the tests now protect

The audit mutated the code by hand, one change at a time, and listed the ones the whole suite let through. Each was applied again against the new tests and **all of them are killed**: the three of the tool-integrity gate (P4-01: one tool passing the other failing its hash, a wrong `--version`, a handshake without a required capability, each on its own tool), a run cancelled before its tool starts (P4-04: the real runner used to answer "cancelled" only because the process it started failed), and the thirteen of P4-07 that can run on any system (a result followed by another event, a failed exit with a printed result, a failed report with a clean exit, a title `mangabind` marked failed that still lists volumes, the shape of a volume number, a blank source id, a negative chapter number, the length of a language tag, an interface with two addresses, an upper-case extension, a folder named like a book, a folder named like a run, a relative environment root).

The packaged window spec also asks the real page to open a window and to navigate away, and fails when either policy is taken out of `window.ts` (both were checked by packaging a build without it: P4-02, E7 and E8). P4-05 was dealt with by the tests that came with the duplicate-chapter fix, which make the fake tools answer with issues and look for them in the result.

**Not done.** Nothing of P4-02 beyond the window is in this part: the decisions of the handlers were pulled out and tested later (see below). The Windows-only separator test of the library paths already runs on the Windows jobs of CI. P4-08 is an observation: the one test that depends on the file system recording creation times was left as it is.

### P5-01, P5-05 and P5-06: the window keeps its place and what the person chose

**What was found.** Re-reading a library after a title's volumes were saved brought the person back to the library screen when the answer arrived, even if they had gone back to the queue, and if they had cleared the queue the screen was about a row that no longer existed: a title bar and nothing else, with no way back (reproduced with the real `App`). A click on a format before the kept settings had been read was silently replaced by the kept value and never saved. And an error about a book that could not be opened was still on screen after "Convert more", on an empty queue.

**What was done.**

- The answer of the second reading only takes the person to the library if they are still on that title's editor (P5-01), and `resolveNavigation` (`src/renderer/lib/navigation.ts`, under the unit gate) shows the queue for any screen about an item that is gone or not in the state the screen needs, so the empty window cannot come back by another road.
- A choice made before the kept settings arrive is put back over them (`use-kept-settings.ts`), in the order it was made, so it is neither lost nor allowed to cost the rest of what was kept; the difference is then saved like any change (P5-05).
- Leaving the results screen clears the error that belonged to it (P5-06). Other screens keep an error across navigation, since a failed run shows its error on the queue it returns to.

**Not done.** P5-02 to P5-04, P5-07 and P5-08.

### P5-02, P5-03, P5-04 and P5-07: the fields, the announcements and the cost of a progress event

**What was found.** Clearing a required number field (cropping power, for one) put the old value back under the cursor, so typing `2` made `12`. A volume number typed with a decimal comma (`1,5`) stayed in the field while the volume kept its old number, and confirming was still allowed. The running screen put every page message in a polite live region, so a screen reader read "Processed page 1 of 200", "page 2 of 200", and so on, minutes behind the work. And every progress event, about once a second, worked out a key over every row of the queue and every volume of every mapping.

**What was done.**

- A number field keeps what is being typed until it is left (`NumberField`): an empty required field keeps its last valid number in the settings and shows it again on leaving, and a new number typed after clearing is taken as typed.
- A decimal comma between digits is taken as a point (`1,5` is volume 1.5), and a number the volume refuses is no longer left in the field: the old one is put back (`isVolumeNumber`, under the unit gate).
- A message about a page is shown and not read out; a message about a stage or a volume is read as before, and each tenth of the work is told in a region for screen readers (`src/renderer/lib/announcements.ts`). Fifty page events change the live regions six times, not fifty.
- The plan key is worked out only when the queue, the process or the options change.
- A book over a gigabyte is shown as "1.5 GB", not "1536.0 MB" (P5-08).

**Not done.** The rest of P5-08: focus around the inline confirmations, the stale job id a Cancel click can send in the instant between two items (not reproduced), the progress events dropped between two jobs (harmless today), and everything about translation (inline English, plurals built by concatenation, a fixed date format).

### P1-08 and P4-06: what is left on disk

**What was found.** Two kinds of leftovers. A run killed while its first book was being made left a half-made file in the pending folder that nothing lists, so nothing could remove it, and the scratch copies of a run's volumes (`mangabound-XXXXXX` in the temporary folder) are removed only when the run lets go of them, so a kill left them; Windows never clears its temporary folder. And every end-to-end run left a pending folder for each spec file, with the converted books in it: each WebdriverIO worker evaluates `wdio.conf.ts` again and named a folder by its own process id, while the cleanup removed only the launcher's, which the apps never used. The audit counted 162 such folders after 18 runs. On the machine used here there were 368 of them, and 431 entries starting with `mangabound` in all.

**What was done.**

- At start the app removes a pending run folder that holds no finished book and has not been changed for a day (`FsPendingRuns.pruneAbandoned`), and the scratch workspaces in the temporary folder that match the name `mkdtemp` gave them and have not been changed for a day (`removeStaleScratch`). "Changed" is the latest time of anything below the folder, since a folder's own time does not move when a file deep inside is written, so a book in the making does not look untouched. A link is not followed.
- The end-to-end suite keeps everything under one folder for the whole run, including the temporary folder of the app and of the spec files, and removes it at the end. The same run on the machine used here, ten spec files, left nothing: 431 `mangabound` entries before, 431 after.
- CI fails the packaged-shell job when anything starting with `mangabound` is left in the temporary folder after the suite (`scripts/verify-no-test-leftovers.mjs`).

**Not done.** The pending folders that earlier runs left on a developer machine are not removed by the app (they are not run folders of the app); they can be deleted by hand.

### P4-02: the decisions in the main process

**What was found.** `src/main` is outside the coverage gate and was checked only by the packaged end-to-end suite. The audit changed fifteen decisions there by hand and ten went through both suites: Save All taking the books of two runs, a selection id that could be replayed, deleting a pending run while a conversion runs, "open book" no longer checking that the path is a file, the folder a Save As remembers, the sharing network kept, the finished runs pruned at quit, the progress of a library, and the two policies of the window.

**What was done.** The decisions were pulled out of the handlers into small units that take what they need as arguments, as `run-job.ts` was, and each has a unit test under the 100% gate: `ipc/pending-decisions.ts`, `ipc/selections.ts`, `ipc/artifact-access.ts`, `ipc/remembered-folders.ts`, `ipc/preferences-state.ts` and `quit-cleanup.ts`. The handlers keep the wiring. Each of the audit's mutants that falls in them was applied again to the new units and is killed; one more mutation (writing `context.lastSaveFolder` instead of `folder`) is equivalent, since the line before it sets them equal. The whole packaged suite passes on the refactored handlers. The two policies of the window have a packaged spec (window open and navigation), checked by packaging a build without each.

**Not done.** The progress a library conversion reports (the audit's E15) is one line of wiring in `conversion.ts` and is still checked by nothing but a person watching; it needs an end-to-end spec that reads the running screen of a library.
