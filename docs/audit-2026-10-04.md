# Five heavy audit passes (2026-10-02), and what has been done about them

- Date of the passes: 2026-10-02. Recorded here: 2026-10-04.
- Commit audited: `677052e` (`main`, after `v0.1.0-alpha.10`).
- Method: five passes, each given one area and one brief, run by Claude Opus on a Linux x64 machine with no access to the GitHub API. They read the code and then reproduced what they claim: they ran the real pinned tools, built the real `.deb`, mounted a real FAT file system, drove the packaged app, and mutated the code by hand (191 mutants against the unit suite). Anything that depends on Windows or macOS is marked as unverified in the reports.
- Passes: 1, trust boundaries and the desktop shell; 2, correctness of the core (mapping, queue, workflows, binding); 3, release, CI and supply chain; 4, whether the tests protect what they say they protect; 5, the renderer.

This is a record, not a plan. It lists every finding with its severity and its present status, and it is updated as the findings are dealt with. The reports themselves are not in the repository; each finding below keeps its ID (`P<pass>-<number>`) so a commit or a pull request can refer to it.

**Before any of it was accepted,** the findings that decide what to do first were reproduced here, on Windows, on the code they were written against: the packaged window can load local files (the `GrantFileProtocolExtraPrivileges` fuse is on), "Stop sharing" waits forever on a stalled download, a 260-character title fails on NTFS only after the whole conversion, a duplicate chapter is dropped without a word by the real `mangabind`, the pending books live inside Squirrel's install root, the end-to-end specs leave 351 folders (about 700 MB) in the temporary folder, and the two sandbox scripts exit 0 on every path.

**Statuses:** _fixed_ names the pull request; _open_ means nothing has been done; _upstream_ means the cause is in another repository.

### P1-01, P1-05 and P1-06: the window

**What was found.** The packaged page was loaded from `file://`, which Electron gives extra privileges by default, so code in the page could read any file the person can, and a CSP that allowed `ws:` and `wss:` let it send what it read to any host. Every permission request was granted (microphone, location, notifications), and starting to share accepted any address the page named, `0.0.0.0` included.

**What was done** ([ADR 0041](adr/0041-the-window-loads-its-page-from-its-own-scheme.md)).

- The fuse `GrantFileProtocolExtraPrivileges` is off. Switching it off alone leaves a window that never loads (Electron cannot read a page from inside `app.asar` over `file://` then; shown by flipping the fuse in the packaged binary), so the packaged page is served from its own `app://mangabound` scheme.
- The page's `connect-src` is `'self'`; the development server's own socket is the same origin as its page, which `'self'` covers (checked in Chromium).
- The request, check and device permission handlers refuse everything except the clipboard write the Copy button needs.
- Sharing starts only on an address the device has now, or on loopback; the check lives in the network adapter, under the unit gate.
- `tests/e2e/window-policy.e2e.ts` runs the attacks against the packaged app: reading a file, opening a socket and a request to a listener the test owns, asking for notifications and the location and querying the microphone, camera and clipboard permissions, sharing on `0.0.0.0`, `::`, `localhost` and an address the device does not have. All four tests fail on a build with the four protections taken out.

**Not done.** P1-10 and P1-11 (the smaller trust assumptions of the shell) and P4-02 (the decisions in `src/main` named by the audit that no test protects) are separate findings and stay open.

### P1-03 and P4-03: stopping to share

**What was found.** `server.close()` answers only when every connection has ended, and nothing ended a response whose reader had stopped reading. "Stop sharing" waited for ever, the sharing state stayed set, and quitting left the process running with no window. The same download left its file open when the reader simply went away, because the file was piped to the response with `pipe`. Three mutants of the authentication (a blank username opening a share that has a password, the navigation feed answered without credentials, the `Basic ` prefix not required) survived the tests.

**What was done.**

- Stopping closes every open connection, so the downloads in progress end and the stop answers at once.
- A connection that does nothing for a minute is closed (`server.timeout`), which is what ends the connection of a reader that fell asleep.
- The file is sent with `pipeline`, so a reader that leaves closes it; leaving halfway is not logged, any other failure is. A failed read now cuts the connection instead of finishing a book that is cut short with an error text.
- An entry of the catalog that is not a file is answered with 404.
- Tests run the real server against a real socket that stops reading (a 64 MiB book): stopping resolves and the reader's connection ends, an idle reader is dropped, the file is closed when the reader leaves, and a failing read is cut and logged. Each was checked by undoing its protection. The authentication gaps have their tests.

**Not done.** Bounding the wait in `before-quit` for the other things it waits on (the workflow, the settings write) is not part of this finding.

### P2-01: two copies of a chapter

**What was found.** A folder often holds the same chapter twice, from two groups. `mangabind` skips every copy, and `mangabind.json` can only say "chapter 2", so placing one copy in a volume in the editor changed nothing: the book shipped without the chapter, and the run ended with "2 books saved." The audit reproduced it with the pinned `mangabind`.

**What was done** ([ADR 0039](adr/0039-mangapress-warnings-are-shown-with-the-results.md), amendment).

- The editor and the main process refuse a draft that places one of two copies of a chapter, with a message that says to remove all but one from the folder. Copies that the file names put in different volumes are left alone. Checked against the real `mangabind` on the audit's folder.
- What the joining step reports as left out (`chapter_conflict`, `chapter_gap`, `empty_chapter`) is now told with the books of a run, for a folder and for a library, instead of being dropped.

**Not done.** `mangabind.json` still cannot name one copy of a chapter, so the choice cannot be made inside the app. Naming a chapter by its folder would take a change in `mangabind`.

### P3-02: pending books and covers inside the installer's folder

**What was found.** On Windows the pending books and the covers lived in `%LOCALAPPDATA%\Mangabound`, which is the folder Squirrel installs the app to (Windows takes `Mangabound` and `mangabound` for one name). On the machine used here an install showed `Pending` beside `Update.exe`. Uninstalling removes the folder the installer made, so a person's converted and unsaved books would go with the app.

**What was done** ([ADR 0026](adr/0026-process-then-save-pending-books.md), amendment).

- The two folders are in `%LOCALAPPDATA%\Mangabound Data` on Windows now.
- At start they are moved from the old place, whole or entry by entry, never replacing anything, leaving the installer's files; a failure is logged and the app starts anyway. Checked on the real packaged app against a scratch `LOCALAPPDATA`: the folders and their contents moved, `Update.exe` stayed, nothing was left behind.

**Not done.** The uninstall itself was not run, since that machine has a real install with real data; the removal is Squirrel's documented behavior. The release checklist now asks for it on a clean machine.

### P3-01 and P3-03: the Linux packages

**What was found.** `scripts/acquire-toolchain.mjs` creates the folder for the bundled tools with `mkdtemp`, which makes it readable by its owner alone, and renames it into place. The folder is copied into the installed app with that mode, so on an installed package it is `drwx------ root`. A person who is not root cannot open it, the app's start-up check cannot hash the tools, and every conversion is refused with "Reinstall Mangabound", which cannot help. The pass built the `.deb` from the audited commit and saw exactly that in `dpkg-deb -c`. The `.rpm` and the Arch package take the same folder, and the `PKGBUILD` already carried a comment about this class of problem, fixed for the first two entries only. The first commit of [#146](https://github.com/gustavommcv/mangabound/pull/146), which added only the check, confirmed all three on CI: the `.deb` (1 of 95 entries), the `.rpm` (1 of 100) and the Arch package (1 of 93) each failed on exactly one entry, `resources/toolchain/linux-x64/` as `drwx------ root`.

It went unnoticed because the app opens fine without its tools, the end-to-end specs run the app as the person who built it, and the only Linux package checks were two scripts that report what they saw and always exit 0 (and, since they run only in `ci.yml`, never for a release). The release notes of alpha.10 and `RELEASING.md` described those scripts as checks of the packages.

**What was done.**

- The folder is made readable and enterable by everyone where it is created, and again when a restored CI cache already holds it (`scripts/acquire-toolchain.mjs`). The `PKGBUILD` now sets read on everything in `/opt/mangabound`, and execute on folders and on files that already run, instead of fixing two entries.
- A check that fails the build: `scripts/verify-package-permissions.mjs` reads the listing of a finished package and fails on any folder others cannot open or file they cannot read, or any program only its owner can run. `.github/scripts/check-package-permissions.sh` lists the `.deb` (`dpkg-deb -c`), the `.rpm` (`rpm -qlvp`) and the Arch package (`tar --zstd -tvf`) and runs it. It runs in `make.yml` and `arch-package.yml` on every change and, since those are the files the release workflow reuses, for every release. The first commit of the pull request had only the check, so its failing run is the proof that the check sees the problem.
- `RELEASING.md`, the release checklist and the repository copy of the alpha.10 notes now say what the sandbox scripts are (diagnostics that cannot fail) and ask for a conversion, not only a launch, on each installed package.

**Not done.** The published alpha.10 files have not been listed: the finding is seen on packages CI built from the same packaging code, and expected, not seen, on the published files themselves. The release notes published on GitHub for alpha.10 still carry the sentence the repository copy no longer does, and editing them is the owner's decision. The audit's stronger suggestion, installing the package and running the app's own start-up verification as a non-root user, is not built; the listing check covers the cause that was found, not every way the tools could become unreachable.

### P1-08 and P4-06: what is left on disk

**What was found.** Two kinds of leftovers. A run killed while its first book was being made left a half-made file in the pending folder that nothing lists, so nothing could remove it, and the scratch copies of a run's volumes (`mangabound-XXXXXX` in the temporary folder) are removed only when the run lets go of them, so a kill left them; Windows never clears its temporary folder. And every end-to-end run left a pending folder for each spec file, with the converted books in it: each WebdriverIO worker evaluates `wdio.conf.ts` again and named a folder by its own process id, while the cleanup removed only the launcher's, which the apps never used. The audit counted 162 such folders after 18 runs. On the machine used here there were 368 of them, and 431 entries starting with `mangabound` in all.

**What was done.**

- At start the app removes a pending run folder that holds no finished book and has not been changed for a day (`FsPendingRuns.pruneAbandoned`), and the scratch workspaces in the temporary folder that match the name `mkdtemp` gave them and have not been changed for a day (`removeStaleScratch`). "Changed" is the latest time of anything below the folder, since a folder's own time does not move when a file deep inside is written, so a book in the making does not look untouched. A link is not followed.
- The end-to-end suite keeps everything under one folder for the whole run, including the temporary folder of the app and of the spec files, and removes it at the end. The same run on the machine used here, ten spec files, left nothing: 431 `mangabound` entries before, 431 after.
- CI fails the packaged-shell job when anything starting with `mangabound` is left in the temporary folder after the suite (`scripts/verify-no-test-leftovers.mjs`).

**Not done.** The pending folders that earlier runs left on a developer machine are not removed by the app (they are not run folders of the app); they can be deleted by hand.

## Order of work

1. **The Linux packages** (P3-01, P3-03): the only High finding, and one that makes the app unusable on a platform it ships for.
2. **The window** (P1-01, P1-05, P1-06, P4-02): the fuse, the policy for the page's network and for permissions, the sharing address, and tests for the decisions in `src/main` that have none.
3. **Sharing and quitting** (P1-03), then **duplicate chapters** (P2-01) and **Windows pending books** (P3-02, after confirming it).
4. **Leftovers on disk** (P1-08, P4-06), then the smaller findings of passes 1, 2 and 5, and the test gaps of pass 4.
5. The process items of pass 3 (P3-04 to P3-07).

A new release follows once the owner decides the list is done; this document does not authorize one.
