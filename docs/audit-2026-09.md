# Architecture and code-quality audit — September 2026

- Date: 2026-09-23
- Scope: architecture and layering, separation of responsibilities, clean code, API/interface design, ease of contribution, test coverage, dependency and security posture.
- Snapshot: 122 commits, 20 accepted ADRs, `main` at the tip after PR #29.
- Method: a fresh, direct read of the layering rules, the largest and most IPC-dense files, the port interfaces, the contributor docs, and the dependency/security posture, plus a wider survey of every `src/renderer` component; grounded against current guidance on Electron security and hexagonal (ports-and-adapters) architecture for 2026, cited inline. Nothing here was assumed from memory of earlier work in this project without checking the code as it stands today.

This is a report, not a plan. It names what to change and why; deciding what becomes a pull request, and in what order, is a separate step.

## What is already working well

Worth stating plainly, because the rest of this document is mostly about what to fix: this codebase is in better shape than most projects its age, on every axis it was asked to check.

- **The layering holds, in practice, not just on paper.** ADR 0001 says the domain imports nothing from Electron, React, Node, or an adapter, and that dependencies point inward. A direct grep across every layer boundary — domain importing Electron or an adapter, application importing an adapter directly, the renderer importing an adapter or a Node builtin, `library`/`opds` importing application code — found **zero violations**. That is not a small thing after 122 commits and 20 ADRs of feature work.
- **Electron's own security guidance is followed to the letter.** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, a denied `setWindowOpenHandler`, and blocked in-page navigation (`src/main/index.ts:825-835`) — this is exactly the current baseline [Electron's own security docs](https://www.electronjs.org/docs/latest/tutorial/security) and independent 2026 guides describe: "never disable context isolation or enable nodeIntegration... a large share of Electron apps with critical vulnerabilities have disabled context isolation or enabled node integration." The preload (`src/preload/index.ts`, 119 lines) exposes a fixed, typed surface on `window.mangabound` and nothing else, matching the recommended pattern of "a minimal preload surface, an IPC allowlist enforced in the main process, and input validation on every argument that crosses the bridge." Every IPC command here is validated against a zod schema before use — this project already does what a lot of 2026 Electron security writeups are still asking teams to start doing.
- **The port interfaces are small, focused, and hard to misuse.** Eight ports under `src/application/ports`, each named for one responsibility (`library-store`, `settings-store`, `opds-server`, `metadata-provider`, `conversion-tools`, `book-file-store`, `network-interfaces`, `process-runner`). `MetadataProviderPort` is a good example of interface design doing real work: it has exactly two methods, `search` and `suggestVolumes`, and _cannot_ be extended to ask for chapters, pages, or images without changing the type itself — the anti-goal from ADR 0005 is enforced by the shape of the interface, not by a comment asking implementers to behave.
- **Contributor documentation is unusually good.** `docs/architecture.md` is one page that states the layers, the rules, a worked example of a conversion end to end, and a table of "to change X, touch these files in this order." `CONTRIBUTING.md` explains what each of the eight `npm run check` gates is for, how to update visual baselines without generating them locally (rendering differs by machine, so baselines come from the CI artifact — a detail a lot of projects get wrong), and how to take a new release of a bundled tool. A contributor who reads both before their first change has a genuinely accurate map.
- **Real-binary testing, not mocked-tool theater.** `tests/unit` records fixtures from the actual pinned `mangabind`/`mangapress` binaries; `tests/e2e` drives the packaged Electron app with WebdriverIO against those same binaries. `npm run capabilities:check` fails the build if either tool has a flag the app does not represent. This is a meaningfully stronger guarantee than the mocked-CLI tests most tool-wrapping projects settle for.
- **Dependency footprint is small and clean.** Eleven production dependencies total (`package.json`), all either Radix primitives, small utilities (`clsx`, `tailwind-merge`, `class-variance-authority`), or `zod`. `npm audit --omit=dev` reports **0 vulnerabilities**. Most of an Electron app's supply-chain risk lives in tooling that never ships; this one keeps what ships small on purpose.
- **The testing pyramid has the right shape.** 42 unit test files (100%-covered layers), 12 component test files, 14 Storybook story files, 7 packaged e2e spec files — many fast, targeted tests underneath a few expensive, high-value end-to-end ones, not the other way around.

## Findings

### 1. `main/index.ts`'s IPC registration is one 420-line function

`registerWorkflowHandlers` (`src/main/index.ts:350-770`) registers roughly nineteen separate `ipcMain.handle` calls in a single function body: input selection, single and batch conversion, metadata search and suggestion, artifact actions, cancellation. Each individual handler is appropriately thin (validate the command, delegate to a workflow, map the result) — the problem is purely organizational. Contrast this with `registerOpdsHandlers` (`216-286`, 7 handlers, one topic) and `registerSettingsHandlers` (`298-348`, 2 handlers) right above it in the same file, which already show the pattern this function should follow: a contributor adding one more IPC command today has to scroll through 420 lines of unrelated handlers to find where theirs belongs, or to confirm it doesn't already exist.

**Why it matters:** this is main's own stated job per `docs/architecture.md` — "builds the adapters, registers the IPC handlers" — and it is explicitly outside the 100% coverage gate, relying on e2e for verification. A file this size and this flat is harder to review by eye, which is the main defense this layer actually has.

### 2. `app.tsx` is the one place doing noticeably more than composing screens

At 1139 lines, `app.tsx` is mostly justified — it is the single owner of the workflow state machine and the only place touching `window.mangabound` (a real, deliberate design choice: every screen below it is "dumb," props in, callbacks out, confirmed by direct reading of `queue-screen.tsx`, `results-screen.tsx`, `library-screen.tsx`). Inside it, though:

- A **domain rule lives in the render body, not `src/domain`.** The device-profile fallback (around `app.tsx:774-785`) computes a business rule — which device to fall back to when the saved one is gone — during render, adjusting state as it goes. The code comment explains _why_ it is written this way (React 19's `react-hooks` lint flags `setState` in effects for this case), but the rule itself is exactly the kind of thing `src/domain/output-profile.ts` already owns for every other device-selection rule.
- **`MappingEditor` is wired up twice with near-identical prop lists** (`app.tsx:932-955` and `985-1000`, ~13 props each), one for a single input and one for a library title. A small wrapper or shared prop-builder would remove the duplication.
- **~24 `useState` calls plus a `useReducer`** in one component (`144-185`) is a lot of independent state to hold in your head at once, even granting that this is deliberately the one centralized place for it.

None of this is prop-drilling in the classic sense — screens are one hop from `App`, not several — it is centralized-state sprawl in a single very large component.

### 3. One instance of imperative DOM reading inside otherwise-declarative JSX

`mapping-editor.tsx`'s "Split before" handler (around lines 605-619) reads a sibling `<select>`'s value with `event.currentTarget.parentElement?.querySelector('select')` instead of holding that value in React state. It is the only place in the renderer survey that reaches into the DOM this way; everywhere else state flows through props and hooks as expected.

### 4. Real UI logic living in component files where `src/renderer/lib` is empty

`src/renderer/lib` — the one renderer directory under the 100% coverage gate — currently holds two files totaling 14 lines. Meanwhile:

- `chapters-from.tsx`'s `OnlinePanel` subcomponent (lines 124-302) owns a genuine async orchestration layer: `AbortController` lifecycle, a search/apply state machine, error normalization. It's self-contained and not unreasonable at its current size, but it is exactly the shape of logic `lib/` exists for, and it currently gets none of the 100%-coverage-gate's guarantee.
- **Click-outside/dismiss handling is implemented twice, independently**: `provider-picker.tsx:59-68` and `share-menu.tsx:50-59` each write their own document-level pointerdown listener to close a popover. There are **zero custom hooks anywhere under `src/renderer`** (confirmed by search) — this is a `useClickOutside`-shaped gap, not a one-off.
- **A repeated row-item visual pattern** (icon-avatar circle + status chip) is copy-pasted across four places — `components/queue/queue-row.tsx:33-59`, `screens/library-screen.tsx:69-92`, `screens/results-screen.tsx:80-89`, `components/mapping/provider-picker.tsx:171-182` — with no shared primitive in `components/ui`, which is otherwise where this project puts exactly this kind of thing (see `mangapress-settings.tsx`'s well-factored `SelectField`/`TextField`/`NumberField`/`ToggleField`, private to that one file but a good local example of the pattern).

### 5. The layering is correct today but not enforced by tooling

The zero import violations found (see "What is already working well") are currently true by convention and code review, not by a lint rule — `docs/architecture.md` itself says the two cross-layer rules are "checked in review." There is no `eslint-plugin-boundaries` (or equivalent hand-rolled `no-restricted-imports` override) making a violation fail CI. For a project that has held this line for 122 commits by hand, this is low-risk today and a real regression risk the moment a second contributor, or an AI coding agent working faster than review can keep up with, adds a shortcut import under time pressure.

### 6. `docs/architecture.md` has drifted slightly behind the last three ADRs

The "Publish" and "What is kept between runs" sections describe `.mangabound/library.json` as the whole story for what OPDS serves. Since ADR 0020, the server also lists untracked files found in the shared folder as a second feed ("Other files"), and since ADR 0019 the port is fixed rather than OS-assigned. Neither is mentioned. This is the smallest finding in this report — a few sentences, not a redesign — but it is real drift, and it's the kind of one-page doc that stays useful only if it keeps getting the five-minute update after a change like this ships.

### 7. Minor Storybook coverage gaps, in the logic-heaviest components

14 of the renderer's non-trivial components have a `.stories.tsx`. The three missing it are, notably, some of the more state-heavy ones: `chapters-from.tsx` (the async search/apply orchestration from finding 4), `provider-picker.tsx` (a hand-built ARIA combobox with keyboard navigation), and `drop-target.tsx`. These are exactly the components where an isolated story — and the accessibility check that comes with every story — would earn its keep the most; right now their coverage is indirect, through whatever parent screen's test happens to exercise them.

### 8. No LICENSE file, despite `package.json` declaring one

`package.json` states `"license": "MIT"`, but there is no `LICENSE` file in the repository root. This was noticed while writing documentation earlier and carried forward to this audit rather than fixed on the spot, since adding one is a real (if small) decision about the project's own terms, not a code change to make unasked. Worth resolving before a public 1.0, not before.

### 9. Already-tracked items, not repeated in depth here

Two items surfaced during this audit were already known and are M8 release-hardening work, not new findings: GitHub Actions are pinned to version tags (`@v7`), not commit SHAs, in both workflow files; and the major dependency upgrades (Vitest 5, TypeScript 7, jsdom 30, and others) are intentionally deferred one at a time rather than taken together. Both are recorded in the project's own backlog already.

## What this suggests, roughly in order of effort-to-value

None of this is committed to; it's the shape a follow-up round of small PRs could take, cheapest first:

1. Add a `LICENSE` file matching the declared MIT license (one file, no code change) — worth a direct answer before it's done, since it's a real term of the project, not just an oversight to patch silently.
2. Update `docs/architecture.md`'s OPDS section for ADRs 0019 and 0020 (five minutes).
3. Split `registerWorkflowHandlers` into a few named registration functions by topic (input, conversion, metadata, artifacts), mirroring `registerOpdsHandlers`/`registerSettingsHandlers` already in the same file. Pure reorganization, no behavior change, easy to review.
4. Add one lint rule enforcing the layer-import boundaries ADR 0001 already states, so the zero-violations result found today stays true by construction, not by vigilance.
5. Pull the device-profile fallback rule out of `app.tsx`'s render body into `src/domain/output-profile.ts`, alongside every other device-selection rule it already owns.
6. Add a small `useClickOutside` hook (or equivalent) in `src/renderer/lib`, and point `provider-picker.tsx` and `share-menu.tsx` at it instead of their own copies.
7. Consider one shared row-item primitive in `components/ui` for the icon-avatar-plus-chip pattern repeated four times, if a fifth use case shows up before this is done — three or four call sites is a judgment call, not an obvious extraction yet.
8. Add stories for `chapters-from.tsx`, `provider-picker.tsx`, and `drop-target.tsx` — the accessibility check alone is likely to earn its cost here.
9. Replace the DOM `querySelector` in `mapping-editor.tsx`'s "Split before" handler with React state.

Items 1-4 are the cheapest with the clearest payoff. Items 5-9 are real but not urgent; none of them are bugs a user would ever notice.
