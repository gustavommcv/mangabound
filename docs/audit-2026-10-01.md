# Audit of what the first two audits did not read (2026-10-01)

A narrow audit made before the release `v0.1.0-alpha.10`, over the parts of the code that [the audit of 2026-09-30](audit-2026-09-30.md) said it had not read, plus the release path. It looked for what could hurt a person using the app or a person trusting its releases, and it reproduced what it claims instead of arguing from the code.

## What was read, and what was not

**Read in full:** the process runner (`src/adapters/process`), both CLI adapters with their argument builders and protocol parsers (`src/adapters/mangabind`, `src/adapters/mangapress`), how `binding-port.ts` checks the paths a tool reports, the OPDS server, feeds and XML escaping (`src/adapters/opds`, `src/opds`), the path and manifest checks of the library (`src/library`), the metadata HTTP client and the MangaDex provider, the toolchain acquisition scripts, the release workflow and a scan of every workflow for risky patterns.

**Run:** `npm audit` for the app and for the site, and the real pinned `mangapress` binary against the inputs behind findings 2 and 3.

**Not read:** `domain/mapping.ts` and the rest of `domain/output-profile.ts` (the validation was used, not reviewed), the settings store, `src/main` apart from what the first audit covered, the renderer, the end-to-end specs, `scripts/` apart from the toolchain scripts, and `.github/scripts/*.sh`. A later pass should start there.

## What is already working well

- **The toolchain is pinned from end to end.** The lock holds the checksum file's hash, each archive's hash and each executable's hash; acquisition extracts only the one expected root entry, runs the version and protocol handshake, and a cache is trusted only after the binary is hashed again (`scripts/acquire-toolchain.mjs`).
- **Nothing a tool reports is trusted as a path.** Every output path from `mangabind` and `mangapress` goes through a containment check before it is used (`checkedChildPath`), and temporary workspaces are removed only under the temporary root and with the app's own prefix.
- **Tools are started without a shell** (`shell: false`, arguments as an array), and the output is capped at 64 MiB.
- **The protocol parsers fail closed.** `mangapress` events are checked for version, shape and sequence, an unknown event type is tolerated, and an event type such as `constructor` cannot reach a method of an object.
- **The OPDS server authenticates before it routes**, compares credentials in constant time, binds only to the address the person chose, and keeps the cause of an error in the app's log instead of the response.
- **The online lookups are narrow:** one fixed base URL, every parameter encoded, a timeout that covers the body, and answers parsed against a schema.
- **The production dependencies are clean:** `npm audit --omit=dev` finds nothing, and the site's audit finds nothing.

## Findings

### 1. A link inside the shared folder leads the OPDS server outside it

**Where:** `serveBook` in `src/adapters/opds/http-server.ts`, with `resolveLibraryFile` in `src/library/paths.ts`.

**Problem:** the fix for finding 1 of the previous audit checks the path as written. It does not follow links. A catalog entry whose path goes through a directory link (or is a file link) is below the folder as written and anywhere on disk once opened.

**Reproduced:** a library with a junction `shelf` to a folder outside it, a catalog entry `shelf/secret.epub`, and the real server: `GET /books/shelf/secret.epub` answered `200` with the outside file's contents.

**Why it matters:** the same reason as before. A folder can come from somewhere else, and an archive extracted on Linux or macOS can carry links. It needs a hostile folder, a catalog that lists the link, and the person sharing that folder, so the likelihood is low, but the file is read with the person's own permissions.

**Priority:** Medium. The fix is small.

**Status:** fixed (this change). The server now follows every link (`realpath`) on the folder and on the file and checks containment again before it opens anything. A link that stays inside the library still works.

### 2. A title or an author that starts with a hyphen makes the conversion fail

**Where:** `buildMangapressArguments` in `src/adapters/mangapress/arguments.ts`.

**Problem:** a value is passed as a separate argument (`--title`, `-Hidden Title`), and `mangapress` reads the second as an option.

**Reproduced** with the pinned binary: `--title "-Hidden Title"` answers `invalid_arguments` ("unexpected argument '-H' found"); `--title=-Hidden Title` works. The title and the author are typed in the book details, and a series can be named that way.

**Priority:** Medium for the people it hits (the conversion fails with a message about arguments), small to fix.

**Direction:** pass the text values as `--flag=value`.

**Status:** open.

### 3. A book whose name starts with two dots cannot be saved to a library

**Where:** `toLibraryRelativePath` in `src/library/paths.ts`.

**Problem:** it refused any relative path that starts with `..`, while the reading side (`resolveLibraryFile`) already knew that a name such as `..Foo.epub` is below the folder. `mangapress` writes `..Foo.epub` for the title `..Foo` (checked), so a title that starts with dots (`...And so on`) failed at publication with "not inside the selected library".

**Priority:** Low to medium. A title that starts with dots is rare.

**Status:** fixed (this change). Both checks use one predicate, `isInsideLibrary`.

### 4. The release path has no gate and no proof of origin

**Where:** `.github/workflows/release.yml`.

**Problem:** a pushed tag builds and publishes. Nothing checks that the tagged commit passed the checks (only that the tag matches `package.json`), and the Release carries no checksums file and no build provenance. The installers are not signed (known, and written in the notes of each release).

**Why it matters:** the person installing has no way to tell that a file is what the workflow built, and a tag on a commit that never went green would still publish.

**Priority:** Medium for the trust the project wants to build; not a blocker for an alpha.

**Direction:** a job that requires the check runs of the tagged commit to be green; a `SHA256SUMS` file among the assets; build provenance attestations (`actions/attest-build-provenance`, which needs `id-token` and `attestations` write on the publish job only). Try it on a release and not on the one that is already a risk.

**Status:** open. Until it is done, the release procedure checks the CI of the exact commit before the tag.

### 5. The app's own dependencies have findings, none of them in what ships

**Where:** `npm audit` at the root.

**Problem:** 58 findings (1 critical, 47 high), all through `@electron-forge/*` 7 (the critical is `tar`, reached from `@electron/node-gyp` and `@electron/packager`) and the `@wdio/*` chain. `npm audit --omit=dev` is clean. Forge 8 is the offered fix. The site's workflow runs `npm audit`; the app's does not, so nobody is told when a production dependency gets a finding.

**Priority:** Low today, because it is build tooling. The missing gate is the part to fix.

**Direction:** run `npm audit --omit=dev` in CI for the app; take the Forge 8 upgrade as its own change with the packaging checks.

**Status:** open.

### 6. Smaller things in the OPDS server and the process runner

- A malformed percent-encoding in `/books/...` (`/books/%E0%A4%A`) throws in `decodeURIComponent` and is answered `500` and logged (reproduced), instead of `400` or `404`.
- The `Host` header is not checked. With sharing left open (no credentials, which ADR 0018 allows) a web page that rebinds its name to the LAN address could read the catalog from the person's browser. Browsers send `Basic` credentials only after a challenge, so a protected share is not affected.
- A title or file name with a control character that XML 1.0 forbids would make the whole feed unparsable for a client (by the XML rules; not reproduced).
- `Basic` over plain HTTP is readable on the local network. It is a stated trade-off (ADR 0018), listed here so it stays visible.
- The process runner passes the app's whole environment to the tools and has no timeout of its own (cancelling is the person's call). `checkedChildPath` is written twice, in `binding-port.ts` and in `conversion-port.ts`.
- The `mangabind` progress parser rejects a stage it does not know, while the `mangapress` one tolerates an unknown event type. A new additive stage in a future `mangabind` would fail a run until the parser is updated; the pin and `toolchain:update` make that a deliberate step.

**Priority:** Low.

**Status:** open.

## What this suggests

1. Findings 1 and 3 are fixed together, because they are the same predicate used in two places; finding 2 is a small separate change. They go in before the release: finding 1 is a security fix and the other two are failures a person can meet.
2. Findings 4 and 5 are process work. The release procedure checks the commit's CI by hand until finding 4 is done; it should not be rushed into the release that depends on it.
3. Finding 6 is a list to take from when the OPDS server is next touched.
